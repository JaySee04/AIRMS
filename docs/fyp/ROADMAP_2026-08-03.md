  key's VALUES are now IC numbers (least-risk faithful replace — the PK/FK column

  12-digit IC). Seeder generates deterministic fake ICs (`icFor`), reseeded;
  verified the app runs IC-keyed end-to-end (session / dashboard / squad, `_id` =
  IC). **STAGE 2:** UI relabelled "Athlete ID" → "IC Number" everywhere the operator
  sees/enters it (athlete profile, ProfileShell, import field, medical search,
  AthleteSearchSelect) + a 12-digit IC hint on the import entry field; CLAUDE.md
  demo table updated. Original concern kept
  for the record: Malaysian IC is *sensitive national PII*; `athleteId`
  ("ATH0001") is a synthetic surrogate key that is deliberately PII-free and is the
  canonical FK across **every** table, is serialised as `_id`, and appears in URLs,
  PDF filenames, and logs. Making IC the primary/foreign key sprays a national
  identifier across the entire surface — the *opposite* of the redaction/minimisation
  we just shipped, and a locked-schema change (CLAUDE.md §Locked decisions).
  **Recommendation: keep `athleteId` as the surrogate key; store `icNumber` as a
  protected attribute on `Athlete`** (shown only where needed, access-controlled,
  never in URLs/filenames/logs). Delivers "IC in the system" without the blast
  radius, and is the defensible viva answer (surrogate keys for PII protection).

## F. Research — vision cost & capacity (answered; no build)

Measured live against `gemini-flash-lite-latest` on both sample PDFs:

- **Tokens per PDF ≈ 8,250** (prompt+images ≈ **7,466**, output ≈ **780**). Stable
  across files because we always send **6 page-images** at render scale 2 + the fixed
  extraction prompt. Bigger/smaller reports barely move it (image count is fixed).
- **Latency: highly variable on free tier** — measured 6s early, then **88s and 107s**
  later the same day. Plan for tens-of-seconds, occasionally >100s per file.
- **Draining the Gemini free tier:** the binding limit is **requests/day (RPD)**, not
  tokens. At ~8.25k tokens/file even a 250k-TPM/min budget isn't the wall; the daily
  request cap is. **Exact free-tier RPM/RPD/TPM for this model change over time — JC
  should confirm at the AI Studio rate-limits page.** Framework: files/day ≈ RPD;
  tokens/day ≈ RPD × 8.25k.
- **Files at once / current capacity:** no hard cap in code. Frontend queues all
  dropped PDFs and extracts **sequentially with 3s spacing**; backend takes **one
  file per request** (20 MB cap each, in-memory). So a batch of N takes ≈ N ×
  (latency + 3s) — at 100 files that's ~15 min (fast) to ~3 hr (slow) and ~825k
  tokens. **For ISN's "hundreds/day": within reach on free tier IF RPD ≥ that count**,
  but wall-clock time and latency spikes make a paid tier (or multiple keys / a local
  model) the safer path at that volume. **Current 3s spacing ≈ 20 req/min** — verify
  it's under the model's free RPM or bump spacing to avoid 429s on big batches.
