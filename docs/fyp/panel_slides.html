sRPE Method
  • Modified Borg CR-10 scale — clamped to 1–10 (not 0–10)
  • Lower bound of 1 prevents zero-load sessions from collapsing the chronic average
  • Captures cardiovascular, neuromuscular & metabolic strain in a single number

Architecture · Database — Panel Response

Database: MongoDB → MySQL  Panel concern was valid — and already resolved

Requirement MongoDB  (NoSQL · inherited prototype) MySQL  (relational · current system)
Athlete → Injury → Activity links Manual references only — no FK enforcement Engine-level foreign keys — referential integrity guaranteed
ACID transactions Optional from v4.0+, session-scoped, added complexity Native — used for SelfReport → Injury promotion atomically
Schema enforcement Schema-less by default; malformed medical records silently accepted Strict schema — invalid rows rejected at write time
Cross-entity queries Aggregation pipelines — verbose, error-prone SQL JOIN — concise, auditable, familiar to medical IT
Data corruption risk High — no FK constraints, history chains can orphan Low — FK constraints + Sequelize hooks enforce write-time consistency
ACID in Practice — SelfReport Approval Flow

When a medical user approves a self-report, the server atomically: (1) marks the SelfReport as approved and (2) inserts a new Injury row — inside a single Sequelize transaction. Both succeed or neither commits. This is a correctness hard requirement for medical data — not optional.

Why Not PostgreSQL?

PostgreSQL and MySQL are architecturally equivalent for this use case — both relational, ACID-compliant, and support FK constraints. MySQL was selected for tooling availability. The panel's concern (NoSQL vs relational) is fully addressed by the migration; the choice between two RDBMSes is secondary.

Clinical Justification — Escalation Gate Design

sRPE Captures Total Body Stress — Not Regional Load

What sRPE Actually Measures

Session RPE on the Borg CR-10 scale reflects the athlete's global perceived exertion — cardiovascular strain, neuromuscular fatigue, and metabolic stress integrated across the entire session. It is not region-specific.

A 90-minute match is a 90-minute match whether the athlete's left hamstring is compromised or not. ACWR sees total load — it cannot see where load is going internally.

The Compensation Cascade
1

Athlete sustains injury — continues training at comparable overall intensity

2

Adjacent and contralateral muscles absorb redistributed mechanical load

3

Those structures were already being loaded — now exceed individual capacity

!

ACWR remains unchanged — it only sees total load holding steady

"New injuries frequently co-occur alongside existing ones, precisely because the athlete's overall training load remains high even when one limb is compromised; the rest of the body absorbs a comparable or greater workload and may already be near its own threshold."

— Dr Thung, ISN (raised directly in stakeholder meeting)
Why Any Active Injury Escalates — Not Just Same-Region
  • sRPE captures systemic load — the whole body operates at the ACWR-implied stress level
  • Injury redistributes internal load onto structures already near their own threshold
  • Region-specific silencing would miss exactly the co-occurrence risk Dr Thung described
  • Gate still requires ACWR > 1.0 — a genuinely low-load session does not escalate
Region-Aware Escalation — Future Enhancement

Escalating only when the session's targeted muscles overlap with the injury region was discussed with Dr Thung and Dr Hoo. It is a meaningful refinement earmarked for a future iteration. It does not invalidate current behaviour — it refines it.

Security — Panel Question

How Does AIRMS Prevent an Athlete from Calling a Medical API Endpoint?

Two Middleware Layers — Applied to Every Protected Route
Layer 1 — auth.js  ·  JWT Verification
Authorization: Bearer <token>
Verifies the token on every request. If the token is missing, expired, or tampered with — the request is rejected before it reaches any route handler. The decoded payload carries the user's role.
Layer 2 — rbac.js  ·  Role-Based Access Control
rbac('medical', 'admin')
Sits on top of auth. Each route declares which roles are permitted. If the authenticated user's role is not in that list — even with a valid token — they receive a 403 Forbidden before the handler runs.
The Attack Path — and Where It Fails
1

Athlete logs in → receives a valid JWT with role = athlete

2

Athlete manually calls GET /api/injuries with that token

3

Layer 1 passes — token is valid and not expired

✕

Layer 2 rejects — role athlete is not in rbac('medical', 'admin') → 403

Frontend Gating vs Backend Security
LayerMechanismRole
Frontend DashboardLayout allowedRoles UX boundary only — prevents accidental navigation. Can be bypassed by a determined user.
Backend auth.js + rbac.js Actual security. Enforced on every API call regardless of how the request originates.
A user who bypasses the frontend entirely — curl, Postman, a custom script — still hits the same two middleware layers on every request. The frontend is never the trust boundary.
Additional Scope Enforcement

Even within a permitted role, athlete-owned data is further scoped by athleteId. An authenticated athlete can only read their own activity records — the route checks req.user.athleteId === req.params.id before querying, preventing horizontal privilege escalation between athletes.
